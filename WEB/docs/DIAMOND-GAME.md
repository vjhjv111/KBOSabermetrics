# DIAMOND 전체 경기 운영

DIAMOND는 기록실 웹사이트 안에서 실행하는 9이닝 야구 게임입니다. 기본 화면은 리그·친선 AI/PvP·마이 플레이어·일정·기록이며 기존 6타석 연습도 남아 있습니다. 이 문서는 ASP.NET Core/SQLite 통합판을 설명합니다. 별도 Sites 6타석 소스 ZIP의 D1 실행 안내와 혼용하지 마세요.

## 실행 환경과 원본 DB 설정

운영 서버는 .NET 8 ASP.NET Core 프로세스 하나입니다. 게임의 JavaScript/CSS는 정적 파일이며 별도 Node 서버가 필요하지 않습니다. 게임 소스를 수정할 때만 Node.js 22.13 이상과 npm을 사용합니다.

| 설정/파일 | 역할 |
| --- | --- |
| `NAVER_SABERMETRICS_DB` 또는 `Site:DatabasePath` | 실제 `sabermetrics_v2.db`의 절대 경로. 게임은 읽기 전용으로 조회 |
| `Site:StateDirectory` / `Site__StateDirectory` | 새 게임 상태 DB·사이트 상태를 저장하는 쓰기 가능한 경로 |
| `diamond_game.db` | 기존 6타석 연습과 대결방 |
| `diamond_career.db` | 리그, 친선 방, 생성 선수·훈련·보상. 각 기능의 테이블은 분리 |
| 게시 폴더 `diamond-data/` | 이전 대결 복원·공용 판정에 필요한 JSON |
| 게시 폴더 `wwwroot/diamond/` | 화면 번들·공개 구장 에셋 |

대용량 원본 DB는 소스 저장소에 포함되지 않습니다. `lib/players.json` 등 기존 2025 선수 스냅샷은 새 시즌 로스터를 대체하지 않습니다. 신규 리그/친선 생성에는 원본 DB가 필요합니다. 리그는 해당 시즌의 10개 구단 각각 타자 9명·투수 1명 이상의 자료가 있어야 하며, 친선은 선택한 두 구단만 이 조건을 충족하면 됩니다. 따라서 8·9개 구단이었던 과거 시즌도 친선 경기에서 선택할 수 있습니다. 원본 파일과 게임 저장 경로는 `wwwroot` 밖에 두어야 합니다. 웹 프로세스에는 원본 읽기 권한과 상태 폴더 쓰기 권한이 필요합니다.

설정은 `Site` 항목의 JSON, 환경 변수, 명령줄에서 읽습니다. `NAVER_SABERMETRICS_DB`가 지정되면 DB 경로를 우선합니다. `SABER_LOCAL_CONFIG`로 별도의 로컬 JSON 설정 파일을 지정할 수도 있습니다. 상대 `StateDirectory`는 게시 앱의 디렉터리 기준이므로 별도 절대 경로 사용이 명확합니다. Render에서는 미설정 시 `/var/data/sabermetrics_v2.db`, `/var/data/state`를 사용하며 지속 디스크가 필요합니다.

## 빌드와 로컬 실행

저장소 루트에서 게임을 빌드합니다.

```sh
cd WEB/diamond-game
npm ci
npm run typecheck
npm test
npm run build
```

출력은 `WEB/frontend/diamond/`입니다. 이 폴더에는 `npm run dev` 명령이 없습니다. 상위 `WEB` 폴더로 이동해 서버를 게시합니다.

```powershell
cd ..
dotnet publish server/src/NaverSabermetrics.Web/NaverSabermetrics.Web.csproj -c Release -o artifacts/diamond-web
$env:NAVER_SABERMETRICS_DB = 'C:/KBO/sabermetrics_v2.db'
$env:Site__StateDirectory = Join-Path (Get-Location) 'work/diamond-state'
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet artifacts/diamond-web/NaverSabermetrics.Web.dll --urls http://127.0.0.1:5080
```

예시 DB 경로를 실제 파일로 바꾼 뒤 `http://127.0.0.1:5080/#diamond`를 엽니다. 원본의 웹용 복사본을 준비하려면 기존 `WEB/scripts/start-local.ps1 -DatabasePath '원본 DB 전체 경로'`도 사용할 수 있습니다. 게임용 SQLite 테이블은 서버가 생성하므로 D1 마이그레이션은 필요하지 않습니다.

Windows에서 npm shim이 잘못된 `npm-cli.js` 경로를 찾는 경우, 게임 폴더에서 설치된 npm을 직접 실행합니다. Node 기본 설치 경로 예시입니다.

```powershell
node 'C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js' ci
node 'C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js' run typecheck
node 'C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js' test
node 'C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js' run build
```

격리된 로컬 Windows 환경에서 사용자 암호화 키 저장소에 접근할 수 없다면 `Development`에 한해 `$env:Site__UseEphemeralDevelopmentKeys='true'`를 설정할 수 있습니다. 기본값은 꺼짐이며 재시작하면 페이지를 새로 고쳐 CSRF 토큰을 다시 받아야 합니다. 운영에서는 지속 키와 HTTPS 설정을 사용합니다.

소스 수정 후 화면 번들과 서버를 함께 배포해야 합니다. .NET 빌드는 `frontend/diamond/`를 `wwwroot/diamond/`로 복사하고 필수 HTML 누락을 오류로 처리합니다. `WEB/Dockerfile`의 .NET 게시 경로도 같은 번들을 사용합니다. 게시 폴더 전체와 상태 저장소를 구분하세요.

## 경기·리그·육성

전체 경기는 3아웃마다 공수 교대, 9이닝, 최대 연장 12회입니다. 홈팀 우세 시 9회 말 생략, 끝내기, 12회 동점 무승부, 주자 진루·득점, 볼넷/사구, 삼진, 병살·희생플라이, 투수 실점 책임과 타순을 처리합니다. 교체한 선수를 다시 투입할 수 없고 진행 중인 투구에는 교체가 제한됩니다.

리그는 10개 구단의 균형 대진표를 생성합니다. 기본은 팀당 144경기·총 720경기, 화면에서 72경기 또는 18경기도 고를 수 있습니다. 내 구단 경기가 끝나면 같은 날 다른 네 경기를 계산해 일정과 순위를 갱신합니다. 공수·경기·일정 자동 진행과 시즌 종료 후 다음 시즌을 지원합니다. 실제 KBO 일정·포스트시즌·트레이드 시장을 그대로 구현한 모드는 아닙니다.

친선은 서로 다른 두 구단의 한 경기입니다. AI 상대 또는 8자리 코드 PvP를 선택합니다. PvP 방장은 홈팀, 참가자는 원정팀이며 공격 시 타격·수비 시 투구 권한으로 바뀝니다. 두 번째 참가자가 오기 전에는 시작하지 않습니다. PvP 자동 진행은 서버에서 거부합니다. 친선 결과는 리그 순위·커리어 XP·개인 누적 기록에 합산하지 않습니다. 주소의 `?room=CODE`는 전체 경기 친선이고 기존 `?match=...`는 타석 연습입니다.

마이 플레이어는 이름, 구단, P/C/1B/2B/3B/SS/LF/CF/RF/DH, 좌/우/양타, 좌/우투, 세 투구폼, 체형·키·피부·머리·장비 색·등번호를 설정합니다. 공용 모델을 돌려 보거나 타격·투구 동작을 재생할 수 있습니다. 생성 선수는 새 리그/경기 로스터에 들어가며 리그의 실제 출전 기록으로 XP·레벨·훈련 포인트를 얻습니다. 훈련은 +2, 최대 95이며 80 이상은 더 많은 포인트를 소비합니다. 신장·체형·외형·능력치는 경기 시작 시 자료와 함께 고정하고 변경은 다음 경기부터 적용합니다. 친선에서는 홈/원정 생성 선수의 외형만 방 생성/참가 시 저장해 양쪽에 공유합니다.

훈련은 역할에 맞는 항목만 허용합니다. 타자/야수는 컨택·파워·선구안·주루·수비 5개, 투수는 구속·제구·체력 3개이며 화면과 서버 모두 다른 역할의 훈련 요청을 막습니다.

리그의 ‘내 선수 차례까지’는 생성 타자의 다음 타석 또는 생성 투수의 조작 차례에서 자동 진행을 멈춥니다. 교체로 출전할 수 없으면 남은 경기 진행 규칙을 따르며, 친선 PvP에서는 제공하지 않습니다.

기존 타석 연습은 6타석 합계 점수로 승부합니다. 원래의 점수 판정과 AI/PvP API는 별도로 유지하며, 전체 경기의 주자·이닝·리그 결과와 합치지 않습니다.

## 조작과 3D 표현

사용자가 직접 조작하는 것은 타격 위치·스윙 시각과 투수의 구종·코스·릴리스입니다. PC는 마우스·방향키·클릭/SPACE, 모바일은 짧은 탭과 투구 버튼을 사용합니다. 모바일 화면을 밀면 페이지 스크롤이며 이동·긴 터치·취소·다중 터치는 스윙하지 않습니다. 공은 서버 시각에 따라 진행하고, 화면을 숨겨도 서버 투구 시간이 멈추지 않습니다.

타격은 야구장 3D 화면을 직접 클릭하거나 짧게 터치해서 합니다. 투수의 구종 선택과 누르고 놓는 투구 버튼은 경기장 안에 배치하고 전체화면에서도 표시합니다. 모바일에서 전체 경기의 구종 목록은 좌우로 밀어 선택하며, 타석 연습은 여러 줄 버튼으로 표시합니다. 버튼 아래에서 스윙 이벤트가 발생하지 않고, 버튼 영역을 제외한 크기로 3D 화면을 맞춰 스트라이크존과 조준 위치를 보존합니다. 투구 준비 중 구종 변경은 잠기며, 버튼에서 포커스가 벗어나거나 터치가 취소되면 충전을 취소합니다.

AI 상대 타격의 첫 공과 다음 공은 기본 자동 진행입니다. 경기장 안에서 자동 투구를 일시정지·재개할 수 있습니다. 결과·타구 연출을 마친 뒤 다음 투구를 요청하고, 숨겨진 탭·다른 게임 화면·저장 창에서는 새 투구를 막습니다. 이미 릴리스된 공의 서버 시간은 계속 진행합니다. 사용자의 직접 투구와 PvP 상대 투구는 자동으로 대체하지 않습니다.

스윙 입력 95ms 뒤의 배트 접촉과 실제 투구 속도를 사용합니다. 타자는 투수의 준비 중 미리 몸을 감고 체중을 싣습니다. 실제 구속 1.00배에서 비행 시간은 `18.44m / 표시 구속`이며 연습·빠르게 설정으로 늦출 수 있습니다. 1.8초 와인드업과 통신 여유를 확보하도록 AI 투구는 요청 후 2.2초, PvP는 2.6초 뒤 릴리스를 예약합니다. 공이 손을 떠난 이후의 실제 구속은 그대로입니다. 입력 시각 범위와 현재 투구 ID를 검증하지만 경쟁전 수준의 부정행위 방지 시스템은 아닙니다.

좌우투 × 오버핸드/사이드암/언더핸드 6폼은 팔 각도, 체중 이동, 스트라이드, 팔로스루가 구분됩니다. 신장을 반영한 손 위치와 서버 릴리스 좌표가 같고 좌우타·양타의 스윙 방향도 바뀝니다. 사구는 준비 자세 몸통·팔·다리·머리·손의 연속 캡슐 충돌로 판정하며 키와 체형 폭을 함께 반영합니다. 체형은 정확한 메시 충돌이 아닌 보수적인 원형 단면 근사입니다. 배트/몸 접촉 순서와 스윙·스트라이크존 예외, 직전 공 통과점 표시를 유지합니다.

야수 7명·포수·투수와 주자 모델을 구장에 표시합니다. 커스텀 포지션을 우선 배치하고 남은 타자를 수비 자리에 채우며 DH는 제외합니다. 실제 미수집 포지션을 추정한 실측 정보로 표시하지 않습니다. 타구 추적, 야수 이동, 주루는 서버 판정의 연출이며 직접 야수 이동·송구·도루·번트 조작은 제공하지 않습니다. 공용 선수는 실제 얼굴 스캔이나 모션 캡처 자료가 아닙니다. 모바일은 렌더 해상도·그림자·먼 세부 표현을 줄이며 실제 성능은 GPU에 따라 달라집니다.

커리어의 선수 미리보기에서는 전신과 얼굴·장비 확대를 전환하고, 좌우 드래그로 회전하거나 스윙·6가지 좌우 투구폼을 재생할 수 있습니다. 얼굴·유니폼·장비와 회복 동작의 최신 변경 및 검증은 [선수 모델 개선 기록](DIAMOND-PLAYER-POLISH-20260913.md)에 정리했습니다.

구장 흙 텍스처 `clay-diff.jpg`, `clay-normal.jpg`, `clay-rough.jpg`는 Poly Haven의 Rob Tuytel 제작 Brown Mud Dry를 변환한 CC0 자료입니다. 잔디·하늘·관중·구장 형상·선수 표면은 코드로 생성합니다. 원본 링크·배포 조건·변환 정보는 [LICENSES.md](../diamond-game/public/assets/stadium/LICENSES.md)에 있으며 번들과 함께 복사됩니다. 이 구장에는 다른 게임의 선수 모델·구장 사진을 포함하지 않습니다.

## 실제 기록과 게임 모델

로스터는 종료된 정규시즌 기록에서 생성합니다. 이적 선수는 ID로 합산하고 시즌·동명이인을 구분합니다. 성적, 투타, 신장, 선구안, 지원 구종별 평균 구속·구사율을 읽으며 미수집/소표본은 기본값과 안내를 사용합니다. 지원 구종은 직구·슬라이더·커브·체인지업·포크·투심·커터입니다.

대결/리그 생성 시 기준일·버전·선수 성적을 저장합니다. 이후 원본 DB가 바뀌거나 일시 중단되어도 저장 경기는 보관한 기록으로 이어집니다. AI 투수가 실제 분포를 사용할 때에는 해당 투수의 위치·구종·구속·좌우타·카운트 조건을 집계하고, 충분한 동일 버전 표본이 없으면 표시된 게임 기본 코스를 사용합니다. 전체 분포와 참가자 식별자는 경기 응답에 내보내지 않습니다.

전체 경기의 안타·수비 결과는 별도 `DiamondSeasonFairBall`에서 실제 타자/상대 투수 기록과 컨택 품질을 함께 반영합니다. 중앙 122m·파울선 근처 100m 구장 펜스에 맞춰 홈런을 판정합니다. 자동 진행은 화면용 몸 충돌 계산을 생략하고 같은 카운트·접촉·수비 규칙과 명시된 사구 기본 확률을 사용합니다. 생성 선수의 기록은 훈련 능력치를 게임용 성적으로 환산한 값입니다. 모두 게임 모델이며 실제 성적·승률의 정확한 재현으로 해석하면 안 됩니다. 수치와 재현 방법은 [전체 경기 밸런스 검증](../validation/DiamondSeason/BALANCE.md)에 있습니다.

## API·저장·접속 제한

| 경로 | 용도 |
| --- | --- |
| `/api/diamond/roster` | 시즌별 실제 선수 목록 |
| `/api/diamond/season` | 소유자의 리그 조회·진행·교체·자동 진행 |
| `/api/diamond/match` | 친선 생성·참가·타격·투구·교체 |
| `/api/diamond/career` | 생성 선수 조회·외형·훈련 |
| `/api/diamond/save` | 내 난수 저장 코드 조회·발급, 코드로 활성 저장 불러오기 |
| `/api/diamond/action` | 기존 6타석 연습 |

리그·친선·커리어는 HttpOnly `diamond_owner` 쿠키로 소유자를 구분하고, 기존 연습은 `diamond_session`을 사용합니다. 같은 브라우저 일반 탭은 쿠키를 공유하므로 PvP는 서로 다른 기기·브라우저·프로필로 시험하세요. 리그·진행 중인 리그 경기·커스텀 선수는 상단 **저장·불러오기**의 난수 코드를 보관하면 쿠키 삭제나 다른 브라우저에서도 복원할 수 있습니다. 코드는 스냅샷이 아닌 같은 소유자의 최신 자동 저장을 가리키며, 입력에 성공하면 새 HttpOnly 쿠키를 발급하고 기존 소유자에 연결합니다. 현재 브라우저의 다른 저장은 삭제하지 않습니다. 친선 방은 별도 초대 코드가 필요하고 6타석 연습의 세션은 복원하지 않습니다.

저장 코드와 쿠키 별칭은 원본 선수 DB와 분리된 `diamond_career.db`에 지속됩니다. 소유자는 자신의 코드를 다시 확인할 수 있으며 코드가 있는 사람은 해당 저장으로 플레이할 수 있습니다. 코드·소유자 식별자를 URL이나 로그에 넣지 않습니다. 서버가 바뀌면 동일한 상태 DB를 이관해야 코드가 유효합니다. 유효한 기존 쿠키를 매 조회마다 재발급하지 않으므로 복원 이전의 늦은 응답이 새 쿠키를 덮어쓰지 않습니다.

친선 방은 활동 후 24시간 보관되며 재접속 시 같은 쿠키와 코드로 이어집니다. 명령은 만료를 갱신하고 조회는 최대 시간당 한 번 갱신합니다. 리그·생성 선수는 해당 상태 DB에 지속 저장됩니다. SQLite의 WAL/SHM을 포함해 안전한 백업을 유지하고, 원본/상태 DB와 비밀 설정을 Git·정적 경로에 공개하지 마세요.

변경 요청에는 요청 ID와 최신 버전이 필요합니다. 동일 요청 재전송은 중복 처리하지 않고 내용이 달라진 재사용과 오래된 버전은 409로 거부합니다. 쓰기 트랜잭션으로 두 사용자 입력을 직렬화합니다. 친선/시즌 GET은 상태 처리 후 ETag를 비교하며 동일 상태는 304로 본문 전송을 줄입니다. 참가하지 않은 사용자는 방을 읽거나 조작할 수 없습니다.

POST는 `/api/session`의 CSRF 토큰과 같은 출처를 요구합니다. 저장 코드/친선/연습 본문은 4KB, 커리어는 8KB, 리그는 16KB 이내입니다. 친선 생성은 분당 소유자 8개·IP 20개·전체 150개, 기존 연습 생성은 IP 16개·전체 180개로 제한합니다. IP 기반 게임 요청 제한은 사이트 미들웨어가 분당 900회로 별도 적용합니다. 저장 코드 복원은 별도의 지속 IP 제한도 적용합니다. 로그인 계정·분실한 코드의 본인 확인 복구·순위 경쟁용 부정행위 탐지는 구현 범위가 아닙니다.

영구 리그의 최초 생성에는 IP당 시간당 20개·하루 100개, 전체 시간당 200개·하루 2,000개 제한을 추가합니다. 제한 카운터는 게임 상태 DB에 저장돼 재시작 후에도 유지되며, 실패한 생성은 롤백하고 동일 요청의 재시도는 중복 차감하지 않습니다. 저장된 리그의 이어하기에는 이 생성 제한을 적용하지 않습니다.

기록실의 다른 탭으로 이동하거나 브라우저가 숨겨지면 게임의 반복 조회·3D 렌더링·자동 다음 투구를 중지하고 복귀하면 재개합니다. 이미 던진 공의 서버 시각까지 정지하는 일시정지 기능은 아닙니다. 빈 커리어 보상 확인은 시즌 전체를 반복 역직렬화하지 않도록 처리합니다.

## 검증

타이틀과 모든 공용 3D 경기장은 실제 한국시간(UTC+9) 06:00~18:00에 주간, 그 외에 야간 배경을 사용합니다. `korea-daylight.ts`의 실시간 감지는 경기 서버 시계·시뮬레이션 배율을 참조하지 않습니다. 경계 시각·포커스·탭 복귀에서 확인하고, 시스템 시계 변경도 최대 1분 이내 반영합니다. 구장을 다시 만들지 않고 하늘·안개·햇빛/투광등·반사 환경·별·도시 창문·전광판 문구만 바꿉니다. `korea-daylight.mjs`는 한국시간 경계와 기기 시간대 독립성, 구독 정리와 자원 재사용을 검사합니다.

일반 방문은 타이틀에서 시작하며 초대 링크는 해당 경기로 바로 들어갑니다. 리그·AI 친선의 직접 플레이 스위치는 `diamond.playPreferences.v1` 브라우저 저장소를 사용합니다. OFF인 공수를 자동 진행할 때는 큐 실행 직전에 구단 저장·경기·이닝·공수·역할·투구 번호가 그대로인지 다시 확인합니다. 타이틀·저장 모달·숨겨진 탭에서 새 자동 진행을 시작하지 않습니다. `title-navigation.mjs`와 `play-preferences.mjs`가 관련 흐름을 검사합니다.

직접 플레이의 결과 공개 시점은 `field-play-timeline.ts`를 기준으로 공·수비·화면이 공유합니다. 뜬공 포구와 땅볼의 1루 송구, 안타의 내야 송구·주루가 끝나기 전에는 기존 점수·아웃·주자·경기 기록을 유지합니다. 최초 복원이 이미 판정된 공부터 시작하면 이전 상태를 추측하지 않고 해당 숫자를 `—`로 가립니다. 서버 판정 시각과 무관하게 접촉 시각에서 계산한 수비 완료 시점에 공개하며, 타구 결과는 1.8초 확인한 뒤 다음 투구를 준비합니다. 재접속으로 오래된 공을 지금 판정한 경우 다음 투구 요청은 서버의 판정 후 900ms 대기도 준수합니다. `result-presentation.mjs`와 `practice-presentation.mjs`가 AI/PvP·리그/연습·3아웃·끝내기·복원을 검사합니다. `sim-*` 전체 자동 진행 명령은 연출 대기를 생략합니다.

게임 폴더에서 실행한 `npm run typecheck`, `npm test`가 통과했습니다. 동작 검사에는 6폼 2,094프레임, 155/185/215cm 좌우타 10,638자세의 손 연결·목표 접촉, 사구 경계·수비 배치, 조준 역투영과 입력/시계 회귀가 포함됩니다. `node tests/pitch-deliveries.mjs --server`는 실제 C# 헬퍼와 TypeScript의 43개 프로필·릴리스·체형 경우를 비교합니다.

저장소 루트에서 아래 검증을 실행할 수 있습니다. 처음에는 .NET 패키지 복원이 필요하며, `<...>`는 실제 절대 경로로 바꿉니다.

```sh
dotnet run --project WEB/validation/DiamondSeason/DiamondSeason.Validation.csproj -- <WEB/diamond-game/lib 절대경로> <임시결과폴더>
dotnet run --project WEB/validation/DiamondMatch/DiamondMatch.Validation.csproj -- <WEB/diamond-game/lib 절대경로> <임시결과폴더>
```

시즌 검증은 합성 DB의 144경기/팀·720경기 일정, 주자/득점/투수 책임, 저장·재시작·동시 요청·커리어 보상을 확인합니다. 친선 검증은 실제 Kestrel HTTP와 서로 다른 두 쿠키 세션으로 216구·12회 게임을 진행하며 AI, 교체 권한, 양쪽 결과 일치, 재전송/경쟁/만료, 원본 오프라인, ETag와 생성 제한을 확인합니다. 홈/원정 커스텀 외형 저장·수정 후 고정·재접속 검사도 포함합니다. 합성 원본 DB 해시가 변하지 않았음을 검사합니다. 최신 상세 결과는 [시즌 검증 기록](../validation/DiamondSeason/VALIDATION.json), [친선 검증](../validation/DiamondMatch/README.md)에 있습니다.

추가 검증은 [기존 타석 API](../validation/DiamondGame/README.md), [DB 로스터](../validation/DiamondRoster/README.md), [실측 AI 투구](../validation/DiamondPitching/README.md)를 따릅니다. `DiamondGame`, `DiamondRoster`, `DiamondPitching` 검증 프로젝트의 현재 Release 빌드도 경고·오류 없이 확인했습니다. 전자는 `Diamond*.cs` 전체를 연결하고 후자는 웹 프로젝트를 참조하므로 확장 프로필의 `GameRatings`, `Position`, `BodyType` 의존성도 포함됩니다. 실제 DB 270경기 밸런스 표본은 팀당 경기당 약 4.5~4.7득점이었으며 전체 리그의 통계적 보증은 아닙니다. 과거 6타석 검증 수치를 현재 전체 경기 검사 수로 합산하지 않습니다.

```sh
dotnet build WEB/validation/DiamondGame/DiamondGame.Validation.csproj -c Release
dotnet build WEB/validation/DiamondRoster/DiamondRoster.Validation.csproj -c Release
dotnet build WEB/validation/DiamondPitching/DiamondPitching.Validation.csproj -c Release
```

자동 검사와 로컬 HTTP 결과는 공개 주소 배포 완료를 뜻하지 않습니다. 배포 후에는 `/#diamond` 진입·탭 복귀, 리그 이어하기·선수 육성, 두 기기 친선 코드와 공수 전환, 양쪽 외형, 모바일 스크롤/투구/스윙, 정적 에셋 404·콘솔 오류를 확인해야 합니다. 프레임이 차단되면 `/diamond/`의 같은 출처 iframe 정책, CSRF 오류면 새 세션 토큰, 자료 오류면 원본 DB 경로와 수집 시즌을 확인하세요.
