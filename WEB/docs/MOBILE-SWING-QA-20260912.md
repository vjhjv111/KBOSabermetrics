# 모바일 첫 탭 스윙 누락 수정 — 2026-09-12

## 재현과 원인

390×844 Chrome 터치 에뮬레이션에서 실제 게임 API와 CDP 터치 입력으로 확인했다.

- ready POST 응답만 공의 릴리스 +350ms까지 늦추면 GET 폴링이 공을 먼저 보여 준다. 기존 코드는 이때 공유 요청 잠금과 busy 상태 때문에 첫 탭을 버렸다. pointerdown/up은 정상 도착했지만 스윙 요청은 없었고, ready 응답 뒤 같은 공에 재탭하면 스윙했다.
- 기존 350ms 제한 때문에 400ms/600ms 터치는 손을 떼는 시각이 같아도 거절됐다. 14px 가로 이동도 브라우저의 pointercancel 없이 앱의 12px 제한에 걸렸다.
- 화면 갱신용 40ms 시계로 입력 가능 여부를 판단해, 실제 입력 시각이 허용 구간에 들어온 경우에도 직전 렌더 상태 때문에 거절될 수 있었다.
- 사전 포커스 유무는 정상적인 80ms 탭 성공 여부에 영향을 주지 않았다.

## 변경

- 스윙만 공유 요청 잠금과 독립적으로 전송한다. 한 투구당 스윙 한 번 제한과 서버의 투구 ID 검증은 유지한다. 독립 요청의 완료/실패는 대기 중인 ready 잠금을 해제하지 않는다.
- 스윙 순간의 현재 시각으로 입력 가능 여부를 판단한다. 같은 시각을 로컬 애니메이션과 서버 inputAt에 사용하고, 기존 95ms 접촉 시간은 유지한다.
- 한 손가락 탭을 최대 700ms, 이동 20 CSS px까지 허용한다. 거리 초과 여부와 시간 제한을 분리한다. 스크롤/핀치 취소, 여러 손가락, 긴 누르기, 범위 밖 이동 후 되돌아오는 동작은 스윙하지 않는다.
- 스윙은 탭을 마칠 때 실행한다. pan-y/pinch-zoom을 유지해 게임 화면에서 세로 스크롤할 수 있다.

## 검증

- TypeScript 검사, 게임 전체 테스트, 번들 빌드, .NET Release publish 통과.
- 실제 페이지 콜백을 실행하는 회귀 테스트를 추가했다. 첫 탭, 입력 시각, 조준 고정, 중복 전송 방지, 잠금 수명, 실패 후 재시도, 새 대결 이후 오래된 응답 무시를 검증한다.
- 지연시킨 ready 응답이 아직 도착하지 않은 상태에서 첫 탭으로 swing POST 1회/HTTP 200을 확인했다. 뒤늦은 ready 응답도 이미 표시된 타격 결과를 되돌리지 않았다.
- 80/200/400/600ms 탭, 포커스 유무, 8/14px 이동에서 첫 탭으로 스윙했다. 릴리스 직전 허용 구간의 탭도 처리됐으며, 허용 구간보다 이른 입력은 계속 차단했다.
- 경기 전/중 타자·투수 화면에서 세로 스와이프가 페이지를 스크롤하고 경기 조작을 발생시키지 않는 것을 확인했다. 이어서 탭 스윙과 투구 버튼 요청도 성공했다.

실제 iPhone Safari 기기 검증은 하지 않았다. 통계 DB와 서버 타격 판정은 변경하지 않았다. 생성된 게임 번들을 frontend와 서버 wwwroot에 함께 반영한다.
