## DB와 배포

실제 원본 `sabermetrics_v2.db`는 계속 읽기 전용으로 조회합니다. 현재 로컬 DB의 2026년 자료는 2026-09-12까지 **타자 285명·투수 290명**, 10개 구단이며, 투타 누락과 전체 기본 구종으로만 구성된 투수는 없었습니다. 신규 리그/친선전은 선택한 시즌의 DB 기록을 스냅샷으로 저장합니다.

Render 기본 경로는 다음과 같습니다. 기존 `Site__DatabasePath` 또는 `Site__StateDirectory` 설정이 있으면 그 설정을 따릅니다.

| 경로 | 사용 |
| --- | --- |
| `/var/data/sabermetrics_v2.db` | 원본 선수·투구 기록 읽기 |
| `/var/data/state/diamond_career.db` | 새 리그·친선·육성·저장 코드 및 제한 카운터 |
| `/var/data/state/diamond_game.db` | 기존 타석 연습 |

게임 테이블은 서버가 자동 생성합니다. 대용량 선수 DB나 로컬 QA 저장 파일은 Git에 포함하지 않습니다. 저장 상태를 이어가려면 상태 디렉터리의 지속 디스크와 백업을 유지해야 합니다. 게임 수정 시 `npm run build`로 생성한 `frontend/diamond/`와 .NET 서버를 함께 배포합니다.

## 통합 과정에서 추가 수정

1. 8·9개 구단이었던 과거 시즌의 친선전도 선택한 두 팀의 타순·투수 조건만 충족하면 생성할 수 있게 수정했습니다. 정규 리그는 10개 구단 조건과 안내를 유지합니다.
2. 기록실 다른 탭으로 이동했을 때 게임의 조회·렌더링·자동 다음 투구를 중지하고, 돌아오면 재개합니다. 이미 던진 공의 서버 시각을 정지시키는 기능은 아닙니다.
3. 영구 리그 생성에 재시작 후에도 유지되는 IP·전체 제한을 추가했습니다. 동일 요청 재시도는 중복 차감하지 않으며, 저장된 경기 진행은 생성 제한과 별개입니다.
4. 보상이 없는 일반 조회에서 전체 시즌 자료를 두 번 더 역직렬화하던 처리를 제거했습니다.
5. 모바일 친선 설정 버튼의 줄바꿈과 푸터 문구를 정리했습니다.
6. 긴 게임 iframe의 아래쪽에 저장 창이 뜨던 문제를 수정했습니다. 실제 부모 화면의 보이는 영역에 맞춰 창을 배치하고 스크롤·크기 변경·모바일 키보드 영역 변경에 대응합니다.

빈 보상 처리 개선 전후를 별도 로컬 실행으로 비교했습니다. 변경 없는 조회의 중앙값은 16.6ms → 9.8ms, 서로 다른 4개 리그를 300ms 간격으로 조회하는 약 15.8초 구간의 서버 CPU 시간은 5.53초 → 3.11초였습니다. 조건부 조회는 모두 304로 성공했습니다. 일부 최대 지연은 개선되지 않았으며 다른 UI 작업이 있는 단일 PC 측정이므로 운영 수용량으로 환산할 수 없습니다. 향후 동시 이용자가 늘면 변경 없는 조회의 쓰기 잠금과 큰 상태 응답을 추가 최적화할 수 있습니다.
