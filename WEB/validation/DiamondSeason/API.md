# Full game / season contract

`GET /api/diamond/season` returns `SeasonResponse` (null save before creation). The root HTTP endpoint supplies its long-lived hashed actor cookie to `DiamondSeasonService.Get(actor)` / `Post(body, actor, token)`. All mutations require a unique `requestId` (8–80 ASCII letters/digits/hyphen/underscore). After create, supply the last `save.version`. Replaying an identical requestId is idempotent; stale versions return 409. GET/tick can resolve a pending pitch and increment version, so the client should adopt each response.

`season-types.ts` is the UI DTO contract. `create` selects a source-record year, a team and pace. Default `seriesPerPair=8` produces a 144-game-per-team, 720-game league (18 round-robin rounds repeated eight times); 1 is an 18-game short season. `start-game` starts your team's next scheduled game. `sim-half` advances the current half inning, `sim-game` finishes your game, and `sim-day` simulates all games that day. `sim-to-player` advances to your custom batter's PA or custom pitcher's defensive turn, starting a fresh game when necessary. It does not skip a current custom-player turn; if the custom player has been replaced, it can finish the game. Finishing your game automatically simulates the other four fixtures and advances the league day. `next-season` is available only after all fixtures finish. Real roster statistics are snapshotted once and retained across seasons.

During your team's offense, use `ready`, `swing`, `take`; during defense use `pitch`, then GET/tick for AI batting. The response's `action` is a `DiamondView` / `ActionView` for the existing 3D scene; `done` means the full game ended, never six PAs. `game` holds nine-slot orders, three bases, outs and line score. `action.role` automatically follows your team's current offense/defense. A resolved pitch keeps its original batter/pitcher for animation until the next pitch starts. After half-inning changes, derive controls from the current role/half, while allowing the previous pitch animation to settle during the 900ms pitch cooldown.

Substitution commands are zero-based `slot` plus a bench `playerId`, or `change-pitcher` with an unused pitcher. They require no live pitch. Re-entry is forbidden; pregame `lineup` sets exactly nine distinct team batter IDs. Fatigue is game pitch count and affects pitch execution; stored real player stats are unchanged.

Construction: `new DiamondSeasonService(stateDirectory, dataDirectory, rosterService, clock: ..., random: ..., rosterOverride: ..., gameCompleted: ...)`. Optional override hook `Func<string,int,DiamondSeasonRosterOverride?>` returns `(Batter, Pitcher, CharacterId, Appearance?)`. It runs before each selected-team game, changing custom-player snapshots only. Completion hook `Action<string,DiamondSeasonGame>` runs **outside** the SQLite transaction. Persisted notifications are retried after restart; rewards must be idempotent by game Id. The root can use a separate table in the same `diamond_career.db`. `PlayerStats` includes batting and pitching game totals keyed by roster ID, including the custom character ID. The service never opens the source database for writing.

## Model details and integration status

- `DiamondSeasonIdentity.Actor(HttpContext)` returns `(Id, Cookie)`, resolving persisted cookie aliases after a save-code restore when `DiamondSaveCodeService` is registered. `SetCookie(HttpContext, Cookie)` issues a 365-day `diamond_owner` only for a new or restored cookie; an existing valid cookie is not rewritten by late responses. Identity is shared with career and friendly endpoints. Program.cs integrates the services and endpoint maps.
- Interactive AI loads the original measured pitch/location distribution when its revision matches the saved season. The profile is pinned in the current duel and survives restart. A changed/unavailable source falls back to saved season arsenal, velocity and discipline, with `action.aiPitching.note` explaining the location model.
- Automatic play samples the saved pitch usage/velocity, strike-zone rate and batter discipline, then uses the same `AiSwing` / `EvaluatePitch` / `FinishPitch` judgments. Only automatic play sets `skipBodyCollision=true`, avoiding screen-pose geometry. Its HBP prior is explicitly a game tuning value, 0.004 per pitch, unless a pinned observed profile provides the smoothed measured rate. Automatic scores are simulated results, not recreated historical game results.
- Full-game fair-ball defense uses hitter and pitcher season records, actual fence distance, and contact quality. Speed affects extra-base advancement and rare triples; fielding affects hit/out probability; stamina affects fatigue onset and automatic pitching changes. Real players without these optional ratings use documented game baselines (speed/fielding 50, stamina 60). Source stats are not edited. Errors, steals, pickoffs, injuries and postseason brackets are not implemented in this regular-season scope. The measured AI balance and model rationale are in `BALANCE.md`.
- Completed fixtures, cumulative stats and the reward outbox commit together. The external reward callback runs after commit, and GET or a retry drains pending rewards. Callback failure never rolls back a completed game. Replayed create requests work without reopening the warehouse.
- Source snapshot changes and custom training do not change an active game. A fresh selected-team game refreshes only the custom-player record.
- `save.appearances` is keyed by roster ID and persists the custom cosmetic snapshot together with the roster. The scene reads this snapshot, so editing hair, colors, number, body or height takes effect consistently from the next game and survives reload. Old saves without the field use the default appearance until the next game captures it.
- `game.participants` records the current batter, pitcher, runners and non-DH fielders when a pitch actually begins. Zero-PA defensive or pinch-running appearances receive one completed-game reward; a player removed before actual participation receives none. Legacy game stats with PA, pitches or runs remain compatible. Career name edits also update the name on career aggregate statistics.
- Career training is role-specific: batters can improve contact, power, discipline, speed and fielding; pitchers can improve velocity, control and stamina. Wrong-role training returns HTTP 400 `CAREER_INPUT` without spending points or advancing the version. Ratings increase by up to 2, stop at 95, and cost 2 PT from 80 onward. Levels, accumulated stats, points and identity persist across new seasons.
- A character created while a game is already underway joins from the next game. `sim-to-player` explains this boundary instead of claiming the existing character has not been created. For participating characters it preserves an existing own-turn live pitch, returns a pitcher after offense, and finishes the game if the character was substituted out.

## Validation

Run `dotnet run --project WEB/validation/DiamondSeason/DiamondSeason.Validation.csproj -- <absolute WEB/diamond-game/lib> <absolute scratch directory>`. Use `--no-restore` after package restore. Optional `--short` runs an 18-game-per-team season; default runs all 144 games per team / 720 fixtures.

The suite creates its own synthetic read-only-source fixture and a separate writable career DB. It checks all hit types, BB/HBP forced runners, inherited-run responsibility, SF/DP, nine-person order, skipped ninth, walkoff limits, twelve-inning draws, direct pitch/swing/take/expiry, six-PAs-not-done, timestamp guards, re-entry restrictions, stale/concurrent requests, restarts, source-offline recovery, career creation/training/reward dedupe, failed callback recovery, custom turn simulation, actual speed/fielding/stamina effects, better-stat/better-input hit probability, HTTP owner cookie/origin/JSON/body limits/ETag, schedule balance, full-season standings and statistical reconciliation, and next-season rollover. The career audit adds appearance persistence/refresh, rename consistency, field-only/runner/bench accounting, an 18-game pitcher career followed into the next season, late creation, training cost/exhaustion/cap/role constraints and HTTP error contracts. Final run: **371 checks passed**, with **144 games per team / 720 fixtures** completed in **8.43 seconds** for the season loop. `VALIDATION.json` records the result; `BALANCE.md` covers a separate 270-game real-DB measurement.
