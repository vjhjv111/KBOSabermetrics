## 변경 전 문제

기존 구조는 SQLite에 저장된 모든 `NormalizedJson`을 시작 시 역직렬화하여 전역 경기 목록에 보관했습니다. 이후 모든 통계 탭과 DataGridView가 동시에 결과를 만들면서 다음 데이터가 중복으로 메모리에 존재했습니다.

```text
정규화 경기 객체 전체
+ 타석·투구·주루 컬렉션 전체
+ 선수별 통계 결과
+ DataGridView 행
```

다년 데이터에서는 메모리가 수 GB까지 증가하고 UI 스레드가 창을 그리지 못하는 상태가 발생할 수 있었습니다.

## 변경 후 시작 흐름

```text
SQLite 스키마 확인
→ 경기 수·연도·팀·구장 메타데이터 조회
→ 최신 연도 경기 헤더 표시
→ 경기 JSON은 선택 탭에서 필요할 때만 읽기
```

`MainForm`에는 전체 DB를 보관하는 `List<NormalizedGame> _games`가 더 이상 없습니다.

## 기존 DB의 1회 마이그레이션

기존 DB에 조회 메타데이터가 없으면 `Games.NormalizedJson`을 8행씩 읽어 다음 인덱스를 생성합니다.

```text
Games 메타데이터 열
Players
GamePlayers
```

각 배치가 끝날 때 커밋하며 모든 경기 객체를 동시에 보관하지 않습니다. 취소 후 다시 실행하면 `IndexVersion`이 갱신되지 않은 경기부터 계속합니다.

## 탭별 조회

- 경기: SQLite 메타데이터만 조회
- 타자/투수 클래식·세이버·WAR: 필터 범위 경기를 한 경기씩 스트리밍 집계
- 리그 상수·파크 팩터: 전체 `kbo_r` 경기를 한 경기씩 집계 후 `ComputedCache` 저장
- 타석·투구·주루·교체·관리·진단: 최대 5,000행 단위 페이지 조회
- 선수 검색: `Players` 테이블 검색
- 선수 개인 페이지: `GamePlayers`로 찾은 해당 선수 경기만 읽고 관련 데이터만 유지

## 대규모 신규 파싱

25경기를 초과하는 입력은 각 경기를 파싱·저장한 뒤 객체를 해제합니다. 전체 입력의 모든 `NormalizedGame`을 결과 목록에 쌓지 않습니다.

## 사용자 환경 확인 절차

1. 기존 프로그램을 종료합니다.
2. 새 ZIP을 별도 폴더에 압축 해제합니다.
3. `NaverSabermetrics.sln`을 열고 `NaverRelay.Gui`를 시작 프로젝트로 설정합니다.
4. NuGet 복원 후 솔루션을 다시 빌드합니다.
5. 첫 실행 시 `SQLite 읽기 인덱스 생성`이 표시되면 완료될 때까지 기다립니다.
6. 작업 관리자에서 메모리가 경기 수에 따라 계속 상승하지 않는지 확인합니다.
7. 프로그램을 종료 후 다시 실행해 인덱스 작업이 반복되지 않고 최신 연도 경기 화면이 빠르게 열리는지 확인합니다.
8. 타자 세이버, 투수 WAR, 타석, 투구, 선수 검색 탭을 각각 열어 지연 로딩을 확인합니다.

## 주의사항

현재 SQLite에는 경기별 정규화 원본이 JSON 형태로 저장됩니다. 처음 조회하는 새로운 필터의 통계는 해당 범위 JSON을 한 번 스트리밍 역직렬화해야 하므로 시간이 들 수 있습니다. 계산이 끝난 결과는 소스 버전과 함께 캐시되어 같은 필터의 다음 조회는 빨라집니다.

실제 컴파일과 Windows 런타임 메모리 측정은 이 작업 환경에서 수행하지 못했습니다. Visual Studio 빌드 및 사용자의 다년 DB 스모크 테스트가 최종 확인 단계입니다.
