# 통합 JSON 수집 회귀 검증

`AuditRegression.csproj`는 별도의 임시 SQLite DB에만 수집합니다. 기존 사용자 DB 경로를 인자로 넘기지 않습니다.

저장소의 `WEB` 폴더에서 .NET 8 SDK로 실행합니다.

```powershell
dotnet run --project ../PC/validation/AuditRegression.csproj -- --combined '<통합 JSON 폴더>' '<검증 출력 폴더>'
```

통합 JSON 폴더에는 아래 네 파일이 필요합니다. 외부 원본은 저장소에 복사하지 않습니다.

- `20260911NCHH02026.json`
- `20260911SKHT02026.json`
- `20260911WOSS02026.json`
- `20260911KTLT02026.json`

출력 폴더 아래 매번 고유한 `combined-*`, `team-er-*` 폴더와 DB를 만듭니다. 팀 자책점 검증만 실행하려면 `--team-er '<검증 출력 폴더>'`를 사용합니다. 출력 폴더의 상위 폴더에 `team-pitcher-source-20260912.html`이 있으면 실제 공식 페이지 스냅숏(622경기, 10팀, 팀 자책점 5,706)도 확인합니다.

## 검증 범위

- 실제 네 경기의 공식 선수 143행을 DB 집계와 비교하고 투구 위치 1,218개, 승패·세이브·홀드 관련 원본 메타데이터를 보존하는지 확인합니다.
- 박스스코어에 없는 2루타·3루타·사구·고의사구·희생번트·희생플라이를 모두 1로 갖는 작은 fixture를 추가해, 결측 열이 0으로 덮이지 않고 루타수에도 반영되는지 확인합니다.
- 잘못된 경기/팀/선수 ID, 불완전 수집, 복수 후보의 이름만으로 연결한 선수, 최종 점수 불일치, 잘못된 이닝을 거부하고 기존 DB가 유지되는지 확인합니다.
- 최신 박스와 과거 통합/별도 공식/네이버 파일의 재수집 우선순위, 공식 박스와 일자별 타점 및 기록 정정 공지의 시각 우선순위를 확인합니다.
- 파싱 후 원본이 바뀌어도 같은 원문에서 경기와 메타데이터를 저장하고, 파일 크기·수정시각이 같아도 내용이 바뀌면 재수집하는지 확인합니다.
- 저장 중간 SQL 오류를 주입해 경기·공식 출처·원본 이력이 모두 함께 롤백되는지 확인합니다.
- 공식 팀 자책점은 전체 시즌의 경기 수/이닝/실점과 경기 집합이 일치할 때만 적용합니다. 월간·상대·구장·상황별/개인 조회의 값 및 개인/팀 WAR는 유지됩니다.
- 공식 팀 기록의 연도 선택 POST, 오류 페이지 거부, 접속 실패 시 동일 범위의 기존 스냅숏 유지, 새 데이터로 범위가 바뀌었을 때의 무효화를 확인합니다.

2026-09-12 검증: 새 통합 검증 2,139개 체크, 기존 분류/별도 공식 중계/타점 회귀 검증 61개 체크 통과. DB와 HTML은 로컬 검증 자료이며 배포 데이터가 아닙니다.

## v8 전체 시즌 검증

```powershell
dotnet run --project ../PC/validation/AuditRegression.csproj -- --combined-season '<통합 JSON 폴더>' '<검증 출력 폴더>' '<읽기 전용 공식 정정 캐시 DB>'
dotnet run --project ../PC/validation/AuditRegression.csproj -- --identity-fixtures '<통합 JSON 폴더>'
```

검증 도구는 캐시 DB를 읽기 전용으로 열고 `OfficialCorrections`, `OfficialDailyBattingSources`가 있으면 임시 DB에 복사합니다. 원본 경기 자료에는 쓰지 않습니다. DB 저장은 실제 프로그램처럼 매번 새로 파싱한 게임에 `SaveGameAndSourceAsync`를 호출합니다.

## v8.1 수집 준비 단계 검증

```powershell
dotnet run --project ../PC/validation/AuditRegression.csproj -- --cache-preflight '<정상 통합 JSON 한 파일>' '<검증 출력 폴더>'
dotnet run --project ../PC/validation/AuditRegression.csproj -- --cache-benchmark '<이전 전체 시즌 검증 DB>' '<동일 통합 JSON 폴더>' '<검증 출력 폴더>'
```

`--cache-preflight`는 실제 저장 API로 만든 독립 임시 DB와 JSON/ZIP 복사본을 사용합니다. 신규·구버전·미검증 파일은 접근 불가인 경우에도 본문 읽기를 시도하지 않는지, 현재 v8 캐시의 파일 크기와 수정시각이 같아도 내용 변경을 감지하는지 확인합니다. 파일별 진행 알림, 시작 전/파일 검사 시작 시/첫 파일 완료 후 취소, 접근 오류와 취소 후 수집 이력 보존을 포함해 20개 체크가 통과했습니다. v8.1은 파서 버전을 올리지 않아 동일한 v8 캐시를 계속 사용합니다.

`--cache-benchmark`는 이전 검증 DB를 읽기 전용으로 열어 `ParsedSources`만 새 임시 DB에 복사합니다. 실제 종료 경기 622개(원문 2,999,101,663바이트)에서 9개 체크가 통과했고 원본 JSON과 이전 검증 DB는 변경되지 않았습니다. 이전 방식의 측정은 매 파일의 본문·해시를 먼저 읽던 사전 검사 순서를 재현합니다. 한 번의 로컬 측정이므로 절대 시간은 디스크 및 파일 캐시에 따라 달라집니다.

| 사전 검사 | 본문 읽기 | 소요 시간 | 결과 |
|---|---:|---:|---|
| 구버전 캐시, 이전 방식 | 622회 | 18.041초 | 622개 재파싱 |
| 구버전 캐시, 수정 방식 | 0회 | 0.009초 | 622개 재파싱 |
| 현재 v8 캐시, 수정 방식 | 622회 | 17.032초 | 동일한 622개 건너뜀 |

현재 버전 캐시는 원문의 실제 변경을 놓치지 않도록 전체 내용 검사를 유지합니다. 해당 검사 시간에는 프로그램이 진행 상황을 표시하고 취소를 처리해야 하며, 이 검증은 GUI의 화면 반응성 자체를 자동 검증하지는 않습니다.
