# V2 제한 사항과 해석 주의점

## 원본 표본과 파서 규칙

핵심 파서 규칙은 제공된 2026년 7경기, 3,646개 이벤트와 추가 단일 경기 JSON을 기준으로 검사했습니다. 과거 시즌에는 아직 관찰하지 못한 문장·이벤트 타입·필드 형식이 있을 수 있습니다.

새 형식은 가능한 한 다음 방식으로 보존합니다.

- 원본 타입과 문장 유지
- `Unknown` 또는 `WasParsed=false`
- `Diagnostics` 경고
- `[JsonExtensionData]`로 미모델링 필드 보존

## 비디오 판독

관리 이벤트와 판독 문장은 보존하지만 모든 과거 판독 사례에 대해 이전 상태를 일반적으로 되감는 완전한 이벤트 소싱 엔진은 아닙니다. 결과 정정 패턴이 추가로 발견되면 보정 규칙이 필요합니다.

## 주자 식별

주자 pcode는 로스터, 이벤트 전 베이스 상태, 활성 타순 슬롯을 조합해 판정합니다. 누락된 로스터, 비정상 교체, 동명이인 문장에서는 pcode가 null일 수 있으며 이름과 원문은 유지됩니다.

## 스트라이크존

`IsInNominalStrikeZone`은 PTS 좌표와 타자별 `bottomSz`/`topSz`, 홈플레이트 폭을 이용한 통계용 기준입니다. 공 반지름, 심판 판정 오차, 포수 미트 위치를 반영한 공식 판정 재현값은 아닙니다.

## 수비 가치

릴레이만으로 정확히 확보하기 어려운 값:

- 타구 속도·발사각
- 수비수 초기 위치와 이동 거리
- 포구 확률
- 포수 프레이밍
- 완전한 DRS/OAA/UZR

따라서 현재 수비 Runs는 제한적이며 완전한 dWAR로 해석하면 안 됩니다.

## WAR 명칭

현재 WAR는 공개된 FanGraphs 방법론을 참고한 KBO용 자체 구현입니다. 데이터 가용성, 파크 팩터 표본, gmLI 근사, 수비 데이터 제한 때문에 FanGraphs MLB 수치나 Statiz 수치와 동일하다고 보장하지 않습니다.

화면의 `*` 표시는 근사·자체 정책이 포함된 지표입니다.

## 리그 상수

리그 상수와 파크 팩터는 적재된 전체 `roundCode == "kbo_r"` 데이터에서 계산합니다. 시즌 일부만 적재되어 있으면 상수도 해당 부분 표본을 반영합니다. 완전한 시즌 결과를 원하면 해당 시즌 정규시즌 경기 전체를 적재해야 합니다.

## 파크 팩터

다년 데이터가 적을수록 구장별 선수 구성과 일정 차이의 영향을 크게 받습니다. 5년 이상 데이터와 최신 연도 가중 평균 사용을 권장합니다.

## SQLite 동시성

SQLite는 단일 사용자 데스크톱과 읽기 중심 API에 적합합니다. 다수 사용자가 동시에 대규모 쓰기를 수행하는 서버 운영 단계에서는 PostgreSQL 어댑터를 추가하는 것이 적합합니다.

## 외부 패키지

V2는 `NaverRelay.Infrastructure.Sqlite`에서 다음 NuGet 패키지를 사용합니다.

```text
Microsoft.Data.Sqlite 8.0.29
```

## 빌드 검증

제작 환경에는 .NET SDK와 MSBuild가 없어 실제 Windows 빌드를 실행하지 못했습니다. 대신 다음을 검사했습니다.

- 52개 C# 파일 구조
- 6개 프로젝트 XML과 솔루션 경로
- 객체 초기화 속성 1,399건
- enum 참조 382건
- 프로젝트 의존 방향
- SQLite 스키마 21개 응용 테이블
- SQL 문 47개 SQLite 컴파일 검사
- 원본/정규화 경기 JSON blob 열 0개
- 7경기 파서 기준
- 동명이인과 투수 최종 라인 필드

사용자 환경에서 최종적으로 다음을 실행해야 합니다.

```text
verify-v2.bat
```
