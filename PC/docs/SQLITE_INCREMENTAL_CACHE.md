# SQLite 영구 캐시 및 증분 파싱

> **이력 문서:** 현재 버전은 `docs/SQLITE_RELATIONAL_WAREHOUSE.md`의 관계형 DB 구조를 사용합니다. 아래 내용의 `NormalizedJson` 캐시/마이그레이션 설명은 이전 중간 버전 기록입니다.

프로그램은 파싱 결과를 다음 SQLite DB에 자동 저장합니다.

```text
%LOCALAPPDATA%\NaverSabermetrics\Data\sabermetrics.db
```

일반적인 실제 경로는 다음과 같습니다.

```text
C:\Users\사용자명\AppData\Local\NaverSabermetrics\Data\sabermetrics.db
```

## 저장과 재실행

- 최초 JSON/ZIP 파싱 결과를 `Games` 테이블에 경기별 정규화 JSON으로 저장합니다.
- 프로그램 재실행 시 원본 JSON/ZIP을 다시 파싱하지 않습니다.
- 시작 시 모든 경기 JSON을 메모리에 복원하지 않고 경기 메타데이터와 조회 인덱스만 읽습니다.
- 입력 파일을 다시 선택해도 경로, ZIP 엔트리, 파일 크기와 수정 시각이 동일하면 `캐시됨`으로 표시하고 건너뜁니다.
- 새 경기 또는 변경된 원본만 파싱하여 DB에 추가하거나 갱신합니다.
- `GameId`가 같은 경기는 중복 추가하지 않고 최신 파싱 결과로 교체합니다.
- 원본 정규화 JSON 파일 저장 기능은 기존대로 유지되며 SQLite 저장은 자동으로 수행됩니다.

예를 들어 5년치 3,600경기가 이미 저장된 상태에서 새 경기 5개를 선택하면 기존 3,600경기는 다시 파싱하지 않고 새 경기만 처리합니다.

## 대규모 입력의 메모리 처리

25경기를 초과하는 대규모 입력에서는 한 경기를 다음 순서로 처리합니다.

```text
원본 1경기 읽기
→ 정규화
→ SQLite 저장
→ 필요하면 normalized.json 저장
→ 해당 경기 객체 해제
→ 다음 경기
```

따라서 5년치를 백필하더라도 모든 `NormalizedGame` 객체를 하나의 목록에 계속 쌓지 않습니다. 소규모 입력만 7경기 샘플 검증과 미리보기를 위해 일시적으로 메모리에 유지합니다.

## 신규 조회 인덱스의 1회 마이그레이션

이전 버전에서 만든 DB에는 화면 지연 로딩에 필요한 메타데이터와 선수 검색 인덱스가 없을 수 있습니다. 새 버전으로 처음 실행하면 기존 `Games.NormalizedJson`을 **8경기 단위**로 읽어 다음 데이터를 보강합니다.

- 경기별 팀·점수·구장·경기 구분
- 타석·투구·주루·교체·진단 건수
- `Players` 선수 검색 인덱스
- `GamePlayers` 경기-선수 연결 인덱스

이 작업은 모든 경기를 동시에 역직렬화하지 않습니다. 각 배치가 끝날 때 DB에 커밋되므로 중간에 취소해도 다음 실행에서 미완료 경기부터 계속할 수 있습니다.

마이그레이션 완료 뒤에는 일반적인 프로그램 시작에서 경기 JSON을 읽지 않습니다.

## 선수 프로필 캐시 버전

선수 개인 페이지에 생년월일·투타·신체정보를 보존하기 위한 파서 캐시 버전은 `player-profile-v2`입니다. 더 오래된 파서 버전으로 캐시된 원본은 같은 JSON/ZIP을 한 번 다시 선택하면 새 버전으로 재파싱됩니다. 이후에는 다시 증분 캐시가 적용됩니다.

조회 인덱스 버전은 별도로 관리되며, 인덱스 버전 변경은 원본 재파싱 없이 기존 정규화 경기에서 1회 재생성할 수 있습니다.

## 계산 캐시

리그 상수·파크 팩터와 필터별 선수 통계 결과는 `ComputedCache`에 저장합니다.

- 전체 `roundCode == "kbo_r"` 데이터 기반 리그 상수와 파크 팩터
- 연도·기간·팀·상대·구장 조건별 선수 집계 결과

새 경기 또는 변경된 경기가 저장되면 DB의 소스 버전이 바뀌므로 이전 계산 캐시는 자동으로 무효화되고 다음 조회 때 다시 계산됩니다.

## DB 초기화

DB를 완전히 새로 만들 때만 프로그램을 종료한 뒤 다음 파일을 삭제합니다.

```text
sabermetrics.db
sabermetrics.db-wal
sabermetrics.db-shm
```

일반적인 업데이트나 오류 확인 과정에서는 먼저 파일을 삭제하지 말고 백업 이름으로 변경하는 편이 안전합니다.
